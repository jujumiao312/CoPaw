# Knowledge Sync：工程知识增量同步工作流

## 一、角色

你现在是一名工程知识库维护工程师。

你的任务不是继续开发代码，而是检查本次开发产生的实际变化，将有价值的工程知识同步到已有知识库。

本工作流适用于任何 AI Coding Agent，不依赖特定工具。

## 二、任务目标

在本次开发完成后：

1. 识别本次实际修改影响了哪些业务功能。
2. 判断哪些已有知识发生了变化。
3. 更新对应的业务功能文档。
4. 记录本次迭代历史。
5. 保证知识文档与实际代码保持一致。

核心原则：

增量更新，不重复生成；以代码为依据，不以记忆为依据；保留历史，不覆盖已有知识。

## 三、第一步：识别本次代码变更

通过 Git 检查：

- 工作区状态。
- 暂存区变化。
- 已提交但尚未合并的本次任务变化。
- 新增文件。
- 删除文件。
- 修改文件。

明确本次任务的基准版本，排除用户原有的未提交修改及无关变更。

分析每个变更文件：

- 修改了什么？
- 修改原因是什么？
- 对应什么业务逻辑？
- 是否改变对外行为？
- 是否改变数据结构？
- 是否改变模块调用关系？

不能只根据 Commit Message 或文件名称推断业务影响。

## 四、第二步：识别受影响的业务功能

读取：

docs/engineering/registry/capabilities.yaml

结合已有功能文档和实际源码，识别本次变更涉及的 CAP。

区分：

- 直接影响的业务功能。
- 间接影响的业务功能。
- 仅涉及技术实现的模块。
- 尚无法确认归属的变化。

如果发现新业务功能：

不要直接创建新的正式 CAP。

先输出新功能候选及其与现有功能的关系，等待确认。

如果一个公共模块被多个功能使用，应分析实际影响，不要机械地更新所有关联功能。

## 五、第三步：分析知识变化

针对每个受影响的 CAP，检查以下内容：

1. 功能概述是否变化。
2. 功能边界是否变化。
3. 业务流程是否变化。
4. 业务规则是否变化。
5. 前端入口是否变化。
6. 后端接口是否变化。
7. 核心代码调用链是否变化。
8. 数据模型是否变化。
9. 模块依赖是否变化。
10. 测试用例是否变化。
11. 已知问题是否得到修复或新增。
12. 是否产生新的兼容性限制。

区分以下变化：

A. 业务行为变化。

B. 业务规则变化。

C. 技术实现变化。

D. 代码位置或调用关系变化。

E. 测试覆盖变化。

F. 纯格式、命名等不影响知识的变化。

只有真正有知识价值的变化才需要写入文档。

## 六、第四步：增量更新知识文档

找到对应的 CAP 文档。

优先更新原有章节：

- 业务流程
- 业务规则
- 前端实现
- 后端实现
- 核心调用链
- 数据依赖
- 模块关联
- 测试用例
- 已知问题

不要删除原有仍然有效的内容。

不要将所有代码修改堆积到迭代记录中。

原有内容失效时，更新为当前真实情况；必要时在迭代记录中保留历史变化。

如果发生跨功能影响，分别更新各自的功能文档。

如果没有产生值得沉淀的知识变化，不要为了更新而修改文档。

## 七、第五步：更新迭代记录

在对应 CAP 文档的迭代记录章节中追加记录。

每条记录包含：

- 日期
- 需求编号（如果存在）
- 需求名称
- 需求类型
- 变更类型
- 业务变化摘要
- 代码变化摘要
- 业务规则变化
- 影响范围
- 测试变化
- 相关代码证据
- 待确认事项

记录应该简洁，重点突出对后续开发有价值的变化。

不能编造需求编号、业务背景或变更原因。

## 八、第六步：更新功能索引

检查 capabilities.yaml。

仅当以下信息发生变化时才更新索引：

- 功能名称或别名。
- 功能状态。
- 前后端入口。
- 核心代码映射。
- 关联模块。
- 测试路径。
- 关联功能。
- 知识完整度。

不需要每次迭代都重写索引。

## 九、第七步：质量校验

逐项检查：

1. 所有文档中引用的文件路径是否存在。
2. 关键类、函数和方法是否真实存在。
3. 核心调用链是否与实际代码一致。
4. 业务规则是否有代码或测试证据。
5. 是否遗漏直接受影响的功能。
6. 是否误修改无关功能文档。
7. 是否存在新旧描述冲突。
8. 是否保留了必要的历史记录。
9. 是否将推测错误地描述为事实。

无法验证的内容必须标记为待确认。

## 十、执行约束

- 本阶段只允许修改工程知识文档。
- 不允许修改业务代码。
- 不允许覆盖整份已有功能文档。
- 不允许删除有效历史信息。
- 不允许编造业务规则和历史背景。
- 不允许仅凭 Git Diff 推断业务含义。
- 不允许将所有技术改动都记录为业务变化。
- 不允许将未经确认的新功能直接注册为正式 CAP。

## 十一、最终输出报告

完成后输出：

### 1. 变更识别
本次识别了多少个变更文件。

### 2. 功能归属
本次影响了哪些 CAP，以及判断依据。

### 3. 知识变化
本次有哪些业务逻辑、规则、代码映射和测试发生变化。

### 4. 文档更新
具体修改了哪些文档、哪些章节。

### 5. 质量校验
哪些检查通过，哪些未通过。

### 6. 待确认事项
列出需要人工确认的业务问题。

### 7. 无需更新的内容
如果某些代码变化不需要沉淀知识，说明原因。

只有完成实际文档修改和质量校验后，才能报告知识同步完成。
